# Detached remote Host service

`RemoteServiceCommandLine` adds four explicit entry points to the existing Host: `--service` owns the kernel and its existing `host.lock`, `--service-start` starts it detached, `--service-bridge` attaches an SSH/WSL stdio connection, and `--service-stop` requests shutdown. Start/bridge/stop use the same selected data directory; attachment and stop require the installed service identity. The desktop's ordinary connection action only attaches; it never deploys or silently starts a service.

`RemoteHostService` reuses **ASP.NET Core Kestrel**, .NET **SocketsHttpHandler/HttpClient**, **ClientWebSocket/WebSocket**, **Channels**, **Process**, cryptographic RNG/fixed-time comparison and **System.Text.Json**. The missing capability was retaining accepted work after a foreground SSH/WSL channel closes. The added adapter routes the existing `WorkbenchHost.DispatchAsync` and notification callback to these mature transports. The original foreground stdio adapter continues to cancel on EOF. There is no second agent engine, HTTP parser, event database, SSH implementation or process scheduler. The code is project authored; no upstream implementation is copied or translated. The desktop's native executable header check references the existing `scripts/verify-release.py` behavior.

The service binds **only IPv4 loopback on an ephemeral port**, with no configurable public URL, configuration-provided listeners, browser Origin, CORS or cookie authentication. It generates a fresh 256-bit bearer for each service instance. The bearer and address live only in a non-symlink, owner-only endpoint descriptor beneath the endpoint's data directory (`remote-service`, directory mode 0700 and files mode 0600 on POSIX). The stable service ID is nonsecret and pinned in desktop settings; every request also supplies it, and the bridge verifies the exact instance identity before attaching. No bearer is put in command arguments, desktop settings or normal diagnostics. Unknown or nonprivate discovery files are refused. Local network fixtures on Windows use the test user's directory; detached production startup is currently POSIX only.

The authenticated loopback API is `GET /identity`, `POST /rpc` and notification-only `GET /events` WebSocket. Kestrel supplies framing, request bounds and network lifecycle. A ready notification establishes the subscription before the bridge forwards RPCs. Bounded per-subscriber Channels disconnect a lagging client instead of blocking or cancelling the kernel. The selected remote transport remains system OpenSSH or WSL; authentication stays on the endpoint. No model API key or account store is copied from the desktop.

## Lifetime, recovery and approvals

HTTP cancellation, WebSocket loss, bridge EOF and desktop exit close only an attachment. Service RPC dispatch deliberately uses Host/service cancellation rather than `HttpContext.RequestAborted`. A disconnected caller may have an **unknown request outcome**; the bridge never retries or replays an action. Explicit `run.cancel`, approval responses and kernel budgets retain their meaning. `--service-stop`, authenticated `remote.service.shutdown`, SIGTERM or actual service exit cancels/joins the kernel and disposes owned command/MCP processes through the existing Host lifecycle.

The existing **SqliteSessionStore** remains the source of truth for accepted prompts, checkpoints, events, messages and pending steering. Reconnect loads bounded `session.view`, `session.events.page`, `session.messages.page` and `session.pending_inputs` projections using original cursors. A coherent message/event boundary in the SQLite snapshot enables count/character-bounded `session.events.since` pages up to a fixed captured source maximum. Latest-view recovery rebuilds unfinished deltas, updates already saved completion cards and then flushes live notifications. Exact event identities and proven source prefixes suppress duplicate presentation without discarding legitimate out-of-order live IDs. Legacy snapshots with no boundary do not replay ambiguous historical deltas. Loading/reconnecting never executes journal actions. `approval.pending` returns registered approval requests, including those reached while no client was connected. An offline approval remains pending until an explicit response, run cancellation or kernel budget/service stop; reconnect never auto-approves it.

Durability covers **loss of clients**, not invisible resurrection after a service crash/reboot. Actual restart calls existing interrupted-run recovery; it does not replay tools, revive old approval completions or claim an unobserved command succeeded. Historical unresolved approval evidence remains in SQLite, while only live registered requests accept `approval.respond`. The daemon is a user process started with native `nohup` and closed standard descriptors, not a new system service manager or automatic boot installer.

Loopback authentication separates unrelated network clients. It does **not** isolate a same-user process able to read the private descriptor, an administrator or kernel; moving work to another account/machine does not itself create an OS sandbox. Application permissions and separately configured OS execution isolation retain their own boundaries. The daemon retains its endpoint-local model credentials and permissions.

## Guided deployment and validation

The explicit deployment window selects a **prebuilt** self-contained POSIX publish from `scripts/publish.ps1`; it does not run an SDK, download a release, copy credentials, accept SSH fingerprints or edit SSH configuration. `RemoteDeploymentPackage` checks every existing `SHA256SUMS` entry, rejects omitted/extra/link/state files, matches Host/Protocol managed assembly hashes to the desktop build, checks native ELF/Mach-O RID and compares native `uname` on the endpoint. The reviewed operation creates new private installation/data directories and refuses existing paths. BCL `TarFile` prepares assets, system `scp` or `wslpath` plus `cp` transfers them, and native SHA-256 tools verify the archive and manifest before startup. Fields remain data arguments with existing POSIX quoting. Failure retains partial remote state for inspection; unknown installations are never replaced or recursively removed.

The Host-only settings in [Directory.Build.targets](../../../Directory.Build.targets) keep the shared managed assembly **AnyCPU** and reuse the C# compiler's deterministic **PathMap** to normalize only the RID-dependent intermediate source/PDB prefix. The native apphost/runtime architecture still follows `RuntimeIdentifier`; actual output and PDB file locations are unchanged. This addresses the observed RID-inferred managed x64 versus local AnyCPU PE headers and `obj/Debug/net11.0/linux-x64/` versus `obj/Debug/net11.0/` debug paths without substituting version labels or source/PDB maps for executable equality. Acceptance requires a fresh matching-configuration Linux publish and local CI build to produce identical `Workbench.Host.dll` and `Workbench.Protocol.dll` SHA-256 values, followed by actual guided deployment. Complete package hashes detect changes but do not authenticate a publisher; the selected prebuilt package remains an explicit trusted input.

`DurableRemoteServiceTests` uses a real local Kestrel listener and actual Host/kernel with deterministic account/model fixtures. It covers authentication/identity/Origin rejection, HTTP cancellation versus work ownership, bridge EOF, notification reattachment, persisted acceptance, explicit cancellation and pending approval/denial after disconnect. `RemoteDeploymentTests` covers manifest integrity, unsafe/extra/missing assets, strict native arguments and RID checks. No fixture makes a paid model call. These checks do not establish acceptance against every external SSH server, WSL distribution, macOS deployment or GUI environment. Report current build/test results separately. The existing real transport workflow in [Desktop Remote](../../Workbench.Desktop/Remote/README.md) remains explicit opt-in.
