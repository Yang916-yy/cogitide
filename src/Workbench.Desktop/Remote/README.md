# Host connections through OpenSSH and WSL

`HostConnectionProfile` stores only a name, endpoint, executable/runtime paths and optional Host data directory. `HostConnectionWindow` edits those preferences. `RemoteHostLaunch` adapts the existing stdio Host to the installed system `ssh` or `wsl.exe`; `WslDistributions` lists installed distributions. [HostClient](../HostClient.cs) retains the single JSON protocol reader, request correlation, cancellation and owned process cleanup used for local connections. The [Host](../../Workbench.Host/README.md) continues to assemble the same agent kernel.

The concrete missing capability was launching that existing Host on another execution environment. Alternatives considered were an SSH library or an HTTP/WebSocket server. System OpenSSH already supplies configuration aliases, keys, agent authentication and known-host verification; WSL already supplies direct executable launch. BCL `ProcessStartInfo.ArgumentList`, streams, JSON and cancellation provide the remaining adapter. There is no second SSH, shell, HTTP, SSE, filesystem or persistence implementation.

The split between a desktop client and an agent executing near its files is a behavioral reference to mature OpenCode/Codex clients. No upstream client implementation is copied or translated here. The adapter is project-authored C#; OpenSSH and WSL remain separately installed system components. Their primary contracts are [OpenSSH command execution](https://man.openbsd.org/ssh.1), [OpenSSH configuration](https://man.openbsd.org/ssh_config.5) and [Microsoft WSL commands](https://learn.microsoft.com/en-us/windows/wsl/basic-commands). This behavior reference is not a claim of a line-for-line OpenCode port.

## Execution and identity boundaries

- The selected Host owns workspace files, Git, command processes, MCP servers, account storage, model requests and model API environment variables. Enter POSIX absolute workspace paths from that endpoint. A Windows path is never normalized into a remote workspace.
- Existing local account stores and model keys are not copied. Before launching SSH/WSL, HostClient removes inherited `API_KEY`/`*_API_KEY` variables and the explicitly configured current/recent provider key-variable names, and removes those entries from `WSLENV`. Other WSL forwarding entries and `SSH_AUTH_SOCK` remain available so normal system authentication works. Configure model credentials and any required noninteractive environment on the remote machine or WSL distribution before connecting. A profile contains no password, private key, account token or arbitrary startup command. Operating-system configuration is still authoritative: an explicitly configured SSH `SetEnv` literal, proxy command or custom credential outside those declared variable names is not rewritten; review that trusted configuration independently.
- SSH uses its existing configuration alias, agent and known_hosts. The adapter explicitly sets `BatchMode=yes`, `StrictHostKeyChecking=yes`, `ForwardAgent=no`, `ClearAllForwardings=yes`, `PermitLocalCommand=no` and `RemoteCommand=none`, and disables a terminal/X11 with `-T -x`. It keeps stdin attached and the child in the foreground despite inherited SSH configuration, and uses OpenSSH keepalives to detect an unresponsive endpoint. It never accepts a host key, rewrites known_hosts, prompts for a password or adds a tunnel. Verify new or changed fingerprints through a trusted channel outside Cogitide.
- A remote SSH account must use a POSIX-compatible command shell. Executable, DLL, dotnet and data directory arguments are individually POSIX-quoted, including spaces, apostrophes and shell metacharacters. SSH receives one `exec` command; profile fields cannot append SSH options. WSL uses `--distribution <name> --exec <executable> <arguments>` directly, without an added shell or login script.
- Connecting requires the matching preinstalled Host. Startup validates the integer wire version and required remote capabilities (`session.view`, `run.continue`). A startup failure terminates the owned local transport and reports fixed diagnostic categories. At most 16 KiB of stderr is transiently inspected; raw stderr is neither shown nor persisted.
- Disconnecting drains an in-flight request write and closes Host stdin under the same BCL `SemaphoreSlim` gate, then waits for exit within one shared two-second grace deadline. Stdout/stderr readers continue draining until that grace ends; an expired deadline still terminates the owned local transport. The Host stops its owned runs/processes on observed EOF. A network partition can delay EOF and stop confirmation; remote outcomes remain unknown until reconnected and inspected. Reconnecting creates a new client and does not replay actions or treat unobserved work as successful. This connection mode does not support detached or offline continuation after losing the client.
- Device-code authentication can be completed through the selected Host. A remote loopback OAuth callback is not tunneled to the local browser. Use device authorization where supported, or arrange supported authentication on the remote endpoint directly.

## Deploying a Host

Deployment is explicit and is never triggered by connecting. Publish the Host from the same source/build as the desktop with the SDK in the repository's `global.json`. For a Linux x64 endpoint, a self-contained example is:

```powershell
./scripts/publish.ps1 -Runtime linux-x64 -HostOnly -OutputDirectory artifacts/host-linux-x64
python scripts/verify-release.py artifacts/host-linux-x64 --require-source-locks --require-unified-kernel
```

Use the target's architecture/RID (for example `linux-arm64` for an ARM64 Linux host) and its required native dependencies. Transfer the **complete published directory**, not only the executable. Place it in a dedicated directory owned by the remote user, make the Host executable there, and use its absolute path in the profile. Deployment artifacts, bundled SDK/runtime files, databases and credentials must remain outside Git.

For SSH, first verify the endpoint's fingerprint and configure a working key or agent with normal OpenSSH tooling. An existing configuration alias can specify username, port and jump host. Copy the published directory with normal `scp` or an existing deployment tool; Cogitide does not edit SSH configuration or install a server. A framework-dependent deployment may instead select an absolute `Workbench.Host.dll` plus the remote `dotnet` executable. A self-contained deployment selects `Workbench.Host` directly.

For WSL, install a Linux distribution separately, deploy a matching Linux Host into that distribution's filesystem, then select its installed distribution name and absolute Host path. Discovery is Windows-only, invokes `wsl.exe --list --quiet`, has a ten-second deadline, bounds output to 64 KiB/128 distribution names and handles WSL's redirected UTF-16/NUL output. Discovery does not start an installation or change the default distribution.

In the desktop, open Host connections, create SSH or WSL, enter the deployment paths, and save/connect. Then open a project by its endpoint-local absolute POSIX path. Nonsecret profiles are retained in the existing desktop settings file. Do not put API keys or tokens in profile fields.

## Validation scope

[RemoteConnectionTests](../../../tests/Workbench.Tests/RemoteConnectionTests.cs) exercise exact launch arguments, quote-preserving paths, rejected SSH option injection, settings round trips, bounded UTF-16 discovery parsing, fake SSH/WSL executable protocol initialization, missing/malformed/incompatible handshakes, redacted authentication/host-key/install errors, EOF shutdown and unknown pending requests. These deterministic local fixtures do not contact personal hosts, make paid model requests, establish that a particular SSH server is configured correctly or substitute for real WSL/platform acceptance testing. Validation results are reported by the repository's current build/test run rather than asserted here.

### Explicit real transport acceptance

[verify-remote.py](../../../scripts/verify-remote.py) requires an explicit `--wsl <distribution>` or `--ssh <alias>` plus a preinstalled `--host-posix <absolute-path>`. It performs no SDK operation, GUI launch, account lookup or model call. On Windows with the usual `/mnt/<drive>` mount, for example:

```powershell
python scripts/verify-remote.py --wsl Ubuntu-24.04 --host-posix /mnt/d/agent/artifacts/remote-host-linux/Workbench.Host
```

The script creates an isolated `artifacts/remote-checks/cogitide-remote-check-*` fixture and initializes its own Git index, so the source repository's correct `artifacts/` exclusion does not hide the generated workspace files. It verifies current capabilities, POSIX paths containing spaces/apostrophes/Unicode, paged inventory/read hashes, explicit generated commands, EOF cancellation and persistence/reconnect without command replay. It retains a JSON result with scope/limitations and nonsecret environment values for [RealRemoteConnectionTests](../../../tests/Workbench.Tests/RealRemoteConnectionTests.cs). That separate test uses the actual Desktop `HostClient` adapter and is explicitly **skipped** in the ordinary suite; opt in with `WORKBENCH_REMOTE_REAL_PROBE=1` and the generated environment. A missing opt-in is never recorded as a successful real connection.

An optional `--loopback-ssh` flag, together with `--wsl`, exercises the installed OpenSSH client against an ephemeral loopback server which launches the preinstalled WSL Host. The test-only dependency is pinned in [requirements-remote-fixture.txt](../../../scripts/requirements-remote-fixture.txt): **AsyncSSH 2.24.1**, upstream commit [`5dbdf18494589a6de7065f9fb89bd5d716f36a35`](https://github.com/ronf/asyncssh/tree/5dbdf18494589a6de7065f9fb89bd5d716f36a35), [EPL-2.0 OR GPL-2.0-or-later license](https://github.com/ronf/asyncssh/blob/5dbdf18494589a6de7065f9fb89bd5d716f36a35/LICENSE). Install it only in a separate private virtual environment when choosing this acceptance test. It is not a production dependency, and no AsyncSSH source is copied or ported. The fixture reuses its [documented server/process redirection APIs](https://asyncssh.readthedocs.io/en/latest/), Python `shlex` for exact allowed argv validation and existing WSL process launch. A custom SSH protocol implementation or system `sshd` installation is unnecessary.

The loopback fixture generates its own host/client keys in a restricted temporary directory outside the repository, uses a dedicated `-F` configuration and exact fixture known-host pin, and never edits personal SSH configuration or known_hosts. It also requires rejection of a mismatched generated host key and a wrong generated client key. `--hold-for-client-seconds <0-300>` keeps this bounded fixture alive while the separately opted-in actual `HostClient` test runs; its temporary SSH configuration exists only during that interval. This establishes loopback SSH interoperability with a real Linux Host and does not claim acceptance against every external SSH server or platform.
