# Native OS tool isolation

`OsIsolationManager` brokers workspace tools through a separate `Workbench.Host --tool-worker` process launched with the official **Microsoft.Mxc.Sdk 1.0.1**. The package's in-process native engine owns containment, policy validation, standard streams and sandbox termination. No AppContainer/PInvoke layer, kernel policy engine, container launcher, JSON-RPC framing, process scheduler, parser or storage implementation is ported into Cogitide.

Windows explicitly selects SDK **ProcessContainer/PSEC**; `Containment.Process` selects **Bubblewrap** on Linux or **Seatbelt** on macOS. Advisory platform discovery is displayed separately from actual launch validation. Unsupported hosts, rejected policies, missing native assets and native launch warnings fail closed when `RequireOsIsolation` is selected. There is no audit, unrestricted, AppContainer or ordinary-process fallback. The pinned NuGet package contains `osx-arm64` assets but no `osx-x64` asset, which is reported as unsupported rather than inferred from the broader upstream platform list. OS-specific prerequisites belong to the upstream guides below; selecting a requirement does not install or elevate anything.

## Policy and ownership

The worker receives a workspace grant, private scratch, read-only application/runtime/system tool directories, an explicit environment allowlist and denied protected Host state. Read-only execution mode grants the workspace **read-only in the native policy**. Other execution modes permit workspace writes while the kernel retains ordinary application approvals. IP egress, ingress and host loopback are denied. Windows retains explicit native clipboard, input injection, external UI-handle/private-atom, desktop-control, IME and system-settings restrictions; its CLR subsystem compatibility choice is explained below. Seatbelt receives native UI lockdown. Bubblewrap has no UI-policy primitive, so the request omits that unsupported section and relies on its private network/mount namespaces and cleared desktop environment. No account/model key, account database, Host data directory, user profile or unrestricted parent environment is passed to the worker. Sensitive common credential directories are explicitly denied. Workspace selection overlapping protected state/scratch is rejected.

Windows CoreCLR links `user32.lib` and cannot initialize under Win32k-syscall-disable: the observed startup fails before managed entry with `0x8007045A` / `0x80008088`, matching [upstream issue 1622](https://github.com/microsoft/mxc/issues/1622). A controlled local SDK probe reproduced the failure with UI disabled and with diagnostics disabled; permitting the CLR's UI subsystem while retaining default Host UI restrictions started the pinned SDK successfully with no native warnings. The policy therefore sets Windows `ui.disable=false`, `clipboard=none`, input injection false, and explicit ProcessContainer `isolation=container`, desktop control false, system settings none and IME false. The [fixed upstream UI resolver](https://github.com/microsoft/mxc/blob/6cc87651b94cc3efe134de42100e236a8ce9633a/src/mxc-sdk/src/core/mxc_common/ui_policy.rs) resolves those settings to the same Host UI restriction flags as full disable, while allowing the imported subsystem inside the container. The Win32k attack surface remains available to the worker; this is not a claim of Win32k lockdown. Filesystem, network, process ownership, credential exclusions and application approval policy are unchanged. macOS retains `ui.disable=true`; Linux omits the section.

The process already has authority over its granted workspace and scratch. This feature does not protect files inside that authorized workspace from an approved shell command. Keep sockets and credentials outside workspace grants. System/runtime grants and the SDK backend's documented baseline remain readable. The desktop and broker continue to run as the user's ordinary processes: merely separating those same-user processes would not create a security boundary. The boundary claimed here is the SDK's native enforcement around the worker and descendants.

One owned worker is retained per chat/workspace, so explicit `lifetime=session` command sessions survive normal run completion. `run.end` stops run-owned commands and disposes run integrations; chat stop, shutdown, lost transport or cancellation during an outstanding execution terminates native worker ownership. A workspace, execution-mode or externally selected integration-configuration change terminates the old worker before launching a replacement, including its retained commands. A lost worker is not reattached, replayed or silently replaced by an unrestricted process. Unknown tool transport outcomes are errors and never successes.

Cleanup strength follows the backend: Windows uses native job ownership, Linux uses the namespace/container lifetime, and the SDK's macOS termination uses its owned process group. Deliberately detached macOS processes keep inherited Seatbelt restrictions, but process-group termination is not proof that every hostile detached descendant exited. No custom process enumerator or native cleanup engine is substituted for that upstream limitation.

The broker exposes no inference, authentication or credential methods to the worker. Microsoft **StreamJsonRpc 2.26.150** owns the live standard-stream protocol and cancellation; its explicit worker interface exposes exactly catalog, execute, bounded raw-byte read, run end and session end. Project-rule reads traverse the worker, preserving original bytes/BOM for hashes. Workspace path checks are reused inside the worker, and native grants protect an actual open when a link changes after those checks. Returned artifact paths are discarded by the broker rather than opening worker-selected paths with Host privileges.

Externally selected `lsp.json`/`mcp.json` are bounded to 64 KiB each and copied into fresh scratch **before** native launch. The broker never writes to worker-controlled scratch afterwards: a replaced file could otherwise become a link-based privileged-write deputy. Read-only runs exclude external servers; other runs reuse the existing LSP/MCP adapters under the same native environment/network/filesystem restrictions. External tool metadata always retains approval. Configured executables outside the grants fail rather than widening the sandbox. Browser checks run under network denial and report blocked connectivity. Worktree administration is omitted because its sibling directories are outside this fixed workspace policy.

Private scratch is intentionally not recursively deleted by the privileged broker after untrusted commands have controlled it. Native handles are terminated/disposed, while scratch removal is left to explicit temporary-file maintenance. A hard process kill cannot report a previously unobserved command as completed.

Startup stderr is always drained, retains at most 4 KiB and exposes at most a scrubbed 2 KiB explicitly untrusted diagnostic together with an observed native exit code. Managed startup failures emit only fixed stage, exception type and HResult. Paths and common credential-shaped values are redacted; broker environment/account contents are never collected. RPC waits have local cancellation/deadline bounds in addition to JSON-RPC cancellation, so an uncooperative peer cannot force the broker to wait indefinitely after its run is cancelled.

## Reuse and provenance

The SDK is reused directly as a pinned NuGet dependency, not adapted line for line. The package nuspec does **not** record a repository commit; this document therefore does not assert a source-identical relationship between the binary and an inferred commit. Upstream behavior/schema documentation was inspected at fixed revision **`6cc87651b94cc3efe134de42100e236a8ce9633a`**:

Direct `.NET Process` alone cannot supply native containment; custom native interop or a second sandbox engine would duplicate MXC without filling a missing capability.

## Verification boundaries

`OsIsolationPolicyTests` checks secret/environment exclusions, protected-root refusal, native read-only grants and absence of ordinary-tool fallback. `OsIsolationWorkerTests` exercises the actual adapters/command subprocesses and run/session ownership **without** claiming sandbox evidence.

`OsIsolationNativeTests` is explicit local native acceptance, enabled with `COGITIDE_TEST_NATIVE_ISOLATION=1`. It launches the real Host worker through MXC and attempts outside-file read/write, protected account-fixture read, host-loopback TCP, parent-fixture termination and inherited environment access, while checking allowed workspace writes and byte-identical instruction reads. Windows additionally attempts `OpenClipboard` and requires access denied without reading, enumerating, clearing or writing clipboard data; a successful open is immediately closed and fails the fixture. It also replaces the worker with a read-only policy and attempts a shell write. It contacts only its own loopback listener and uses no real credentials, models or paid services. The Unix network fixture requires `python3` installed under the granted system tool paths.

A skipped native fixture, successful capability probe, policy-construction test or successful ordinary dispatcher fixture does not prove OS isolation. Report the actual native platform/backend and denial-test result separately. These are functional security/lifecycle checks; no benchmark, academic benefit, three-platform verification or unrestricted same-user Host protection is claimed.

Recorded local acceptance on **2026-11-02**: the two actual Windows ProcessContainer native fixtures and five policy fixtures passed (**7/7**) under the pinned .NET SDK. This exercised outside-file read/write and protected Host-state denial, host-loopback TCP denial, parent-fixture termination denial, cleared inherited environment, allowed workspace writes, native read-only grants, `OpenClipboard` returning access denied without reading clipboard contents, retained session commands and cancellation/cleanup. This record covers the tested Windows host and exact policy above; it is not Linux or macOS native acceptance.
