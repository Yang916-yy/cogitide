# Git review and publication

`RepositoryReview.cs` and `ReviewActions.cs` integrate the installed **Git CLI** with the existing `WorkspaceService` physical-path, SHA-256, process, output-budget and cancellation helpers. The Desktop uses shared `ReviewContracts` through the selected stdio Host. This module is independent C# application integration: no upstream source or proprietary frontend code was copied or adapted. Git's command contracts are behavior references; the installed executable owns status, index locking, patch generation/application, checkout, commits and transport. No new Git engine, process scheduler, authentication store or general unified-diff parser was added.

The relevant primary specifications are [`status --porcelain=v1 -z`](https://git-scm.com/docs/git-status), [`diff`](https://git-scm.com/docs/git-diff), [`apply`](https://git-scm.com/docs/git-apply), [`restore`](https://git-scm.com/docs/git-restore), [`commit`](https://git-scm.com/docs/git-commit), [`push`](https://git-scm.com/docs/git-push) and [`gh pr create`](https://cli.github.com/manual/gh_pr_create). Existing provenance and notices remain in [Tools dependencies](../DEPENDENCIES.md).

Git creates each single-file diff. A small framing expression recognizes only Git's `@@` delimiters and range metadata; the file header and hunk bytes are preserved verbatim, including no-newline markers. The server resolves a selected hunk ID from a newly generated snapshot; clients cannot submit arbitrary patch text. Git `apply --check` and `apply` validate and apply the fragment, with no fuzzy matching, whitespace repair, reject files or whole-file fallback. Added/deleted files and mode changes use whole-file actions. Rename halves are shown as deleted/added paths (`--no-renames`); Git recognizes the final rename at commit time. Binary changes are whole-file only. Conflicts, submodules and linked/unsupported paths require inspection in Git.

The existing [Editing](../Editing/README.md) adapter accepts the Codex-style `apply_patch` format, not Git's unified format, and cannot supply index-only operations. Reusing installed Git avoids importing a second native Git implementation such as LibGit2Sharp merely to split display hunks. The only missing presentation capability is identifying boundaries/ranges in Git's own bounded output; the small framing expression supplies that, while all semantic validation and writes stay in Git. Scoped hunk application runs from the repository root with Git's `--directory` option; running a relative patch from a selected subdirectory can otherwise return success while skipping paths.

A review snapshot binds the physical selected directory and repository, HEAD/branch, the **entire staged index delta**, scoped status and SHA-256 of changed working files plus their generated patches. Every action rereads that state and rejects stale observations. A selected subtree can stage/unstage/discard its own paths; commit and publication require the repository root so that staging outside the selected directory cannot enter an unseen commit. Bounds are 200 changed paths, 32 MiB changed file bytes, 256,000 characters per patch and 1,000,000 total patch characters; over-budget observations fail explicitly instead of presenting partial state as complete.

Staging applies the working/index delta to the index. Unstaging applies the staged/HEAD delta in reverse to the index. Discard applies a working/index hunk in reverse, or restores one entire path **from the index**, retaining staged changes and unrelated working changes. Discarding an untracked path deletes only that one checked file, never a directory or ignored siblings. Destructive discard requires a concrete UI confirmation and an explicit server flag. Shared in-process repository/path locks serialize these actions with ordinary checked edits. Git's index locks protect native index writes; physical checks and expected snapshots are application safeguards, not an OS sandbox against a hostile concurrent filesystem process.

Commit never stages implicitly, uses exactly the reviewed index, and requires an explicit message/click. Hooks and commit signing are suppressed in this review flow to avoid implicit extension execution or hidden signing UI; normal Git remains available for projects requiring those steps. Push is a separate explicit confirmation, uses the configured upstream, and never force-pushes or changes configuration. Pull request creation is another explicit confirmation through installed `gh`, with `--head` so it does not auto-push. Git/gh retain their existing endpoint credentials; the UI has no credential fields, raw CLI diagnostics are not returned, and only a validated HTTPS pull request URL is exposed. Timeout/truncated observation is reported as an unknown outcome requiring inspection before retry. Review comments are anchored to path, area, hunk/range and snapshot, then added to the user's draft prompt; they never submit an agent task automatically.

`GitReviewTests` uses temporary real Git repositories, including independently staged/working hunks in one file, stale bytes/global staging, Unicode untracked files, rename commit ownership, scoped review, poisoned ambient `GIT_*` variables, ancestor links and a local bare push target. `ReviewUiTests` exercises the compiled Avalonia window headlessly: opening/selecting/adding feedback cannot commit or publish, selected hunk actions carry their snapshot, and scoped commits remain disabled. Fixtures do not create a remote pull request, invoke a model, establish paid-model effectiveness or substitute for visual platform acceptance.
