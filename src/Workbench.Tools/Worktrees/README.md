# Managed Git worktrees

`ManagedWorktrees.cs` exposes `create_worktree`, `list_worktrees`, `worktree_status` and `remove_worktree`. It reuses **Git CLI** for branch validation, commit resolution, checkout, index, registration, status, locking and removal; .NET `Path`, `FileStream`, System.Text.Json source generation, SHA-256 and the existing `WorkspaceService` process/output/cancellation helpers provide the integration. No Git object database, checkout engine, Git ignore parser or storage framework was added.

Git's documented [`worktree`](https://git-scm.com/docs/git-worktree), [`rev-parse`](https://git-scm.com/docs/git-rev-parse), [`check-ref-format`](https://git-scm.com/docs/git-check-ref-format) and [`status`](https://git-scm.com/docs/git-status) contracts are the implementation source. The product behavior (isolated managed checkout and explicit cleanup) is comparable to mature coding agents; this file is independent C# application integration of Git, not a port of Codex or OpenCode worktree code. Existing upstream behavior references and original notices remain in [Tools dependencies](../DEPENDENCIES.md).

Creation resolves a requested start point to a commit before checkout and creates a **new** branch (`codex/worktree-<id>` by default). It never resets an existing branch. Managed checkouts live outside the source tree, under a primary-worktree sibling `.cogitide-worktrees/<common-directory-hash>/<id>`. Ownership metadata lives in that bucket's `.metadata` directory, outside both Git source and Git internals. The full canonical Git common directory binds records to a repository; the creating chat owns removal. Selecting a managed checkout resolves the same management bucket through Git's primary worktree record.

`create_worktree` and `remove_worktree` require the existing tool approval gate. They intentionally write to this narrowly computed sibling directory; read-only execution omits both tools. Paths and every existing ancestor are checked for symlinks/junctions, IDs must be GUIDs, and manifest paths are validated against the computed managed bucket. Git is invoked through `ProcessStartInfo.ArgumentList`, with `-C` and the existing sanitized environment, never through shell interpolation. These are application checks, not an OS sandbox or protection against a hostile local process racing filesystem changes.

The selected workspace must be the Git checkout's top level or a physical subdirectory of it. Bare repositories, selections inside `.git`, configuration that redirects the selected directory to an unrelated checkout, nonabsolute Git-reported directories and control characters in directory names are rejected before creating metadata. The Git common directory and management-bucket ancestors must remain physical paths; no existing metadata or ancestor link is adopted as trusted ownership.

On macOS only, the operating system's exact `/var`, `/tmp` and `/etc` root aliases are normalized to `/private/var`, `/private/tmp` and `/private/etc` before repository identity, boundaries and link checks. BCL `DirectoryInfo.ResolveLinkTarget(true)` must confirm each exact expected target. This accommodates normal macOS temporary directories without following arbitrary user links: all remaining ancestor symlinks/junctions are still rejected. Manifests, returned paths and repository hashes use the physical spelling, so an alias and its physical route identify the same managed worktree.

All invocations reuse `WorkspaceService.ExecuteAsync`'s existing Git environment policy, which removes ambient `GIT_*` overrides (including repository, worktree, index and config redirection) and API-key variables. Git's `--no-optional-locks` suppresses optional index refresh during read-only status inspection while preserving locks required for mutations. Managed checkout adds Git's standard `-c core.hooksPath=/dev/null` override to suppress an implicit `post-checkout` hook. This does not disable every Git extension mechanism: configured checkout filters may still execute with the user's permissions, so managed worktrees remain an approved application workflow rather than an OS sandbox.

Creation persists ownership intent atomically before invoking Git. A failed/cancelled checkout leaves inspectable state; it is not automatically retried, force-cleaned, pruned or adopted. Listing reports registration and path presence and uses the existing bounded JSON page helper; inventory can change between pages. Status reports a bounded excerpt and an explicit truncation flag. At most 100 managed records are admitted per repository.

Removal requires the creating chat, matching repository/path metadata, current Git registration and a clean status including **untracked and ignored** files. Git repeats its own checks at removal and is never passed `--force`. The branch is retained. Unknown registration, changed ownership metadata or missing paths require explicit inspection; the adapter does not recursively delete an arbitrary directory, delete branches, merge changes, prune or rewrite history. Switching a chat to the returned checkout is a separate explicit workspace operation.

[ManagedWorktreeTests](../../../tests/Workbench.Tests/ManagedWorktreeTests.cs) uses local Git repositories with spaces in paths to exercise checkout isolation, the same bucket from a managed checkout, clean removal/retained branches, modified/untracked/ignored preservation, repository/chat ownership, forged metadata and preflight rejection. Additional preflights cover bare/`.git` selection, allowed selected subdirectories, control characters and an actual managed-bucket ancestor junction/symlink with untouched outside-target evidence. A macOS-only fixture creates through `/var`, lists/removes through `/private/var`, checks identical ownership and rejects a custom ancestor link. A nonparallel collection exercises poisoned ambient repository/worktree/index/config variables against an untouched foreign repository; another fixture installs a `post-checkout` hook and verifies managed checkout suppresses it. This is functional workflow validation, not a claim of measured research benefit.
